Before you start

Do not begin this until the mesh swap works

Bottom line: This chapter adds falling chunks on top of a working collapse. If the mesh swap in Chapter 1 is not finished, go back and finish it — you will otherwise have no destruction at all if you run out of time here.

Confirm all four are true

Check each one in the running game before continuing. Every step below assumes all four.

  1. Punching a building reduces its health and prints values in the Output panel.
  2. The building visibly changes appearance at 50% health.
  3. The building flattens to rubble at 0% health and you can walk over it.
  4. script/building.gd contains a _collapse() function and typed @onready references named intact, cracked, rubble and shape.
Warning — this is optional work. A jam entry with a clean mesh-swap collapse scores better than one with beautiful debris and an unfinished level. Only continue if you are ahead of schedule.
Note — this chapter needs no software but Godot. The chunks are generated from Godot's own box primitives, which takes roughly 30 minutes. Chapter 3 upgrades those boxes to real fractured shards using Blender, and builds directly on the code below. Finish this chapter first.

Physics debris

Generate the chunks in Godot

Bottom line: Build the debris from plain boxes in code. At low-poly scale a skyscraper falling apart into 24 boxes reads perfectly well, and it needs no modelling software at all.

1. Add a container for the chunks

One empty node holds every chunk, so you can free them all together.

  1. Open scene/building.tscn and select the Building root node.
  2. Press Ctrl+A, add a Node3D, rename it to Chunks.
  3. Leave its Position at 0, 0, 0.
Expected: an empty Chunks node under Building, alongside Intact, Cracked and Rubble.

2. Build the chunks in code

Add this to script/building.gd. It fills the building's volume with a grid of frozen boxes when the scene loads.

What "frozen" means: a RigidBody3D with freeze = true ignores gravity and forces entirely. It sits exactly where you put it until you release it, so it costs almost nothing while the building is intact.

# Chunk grid: 2 wide, 3 tall, 2 deep = 12 chunks per building.
@export var chunk_cols: int = 2
@export var chunk_rows: int = 3
@export var building_size: Vector3 = Vector3(12.0, 40.0, 12.0)

@onready var chunks: Node3D = $Chunks


func _build_chunks() -> void:
    var size: Vector3 = Vector3(
        self.building_size.x / self.chunk_cols,
        self.building_size.y / self.chunk_rows,
        self.building_size.z / self.chunk_cols)

    for x: int in range(self.chunk_cols):
        for y: int in range(self.chunk_rows):
            for z: int in range(self.chunk_cols):
                var body: RigidBody3D = RigidBody3D.new()
                body.freeze = true
                body.freeze_mode = RigidBody3D.FREEZE_MODE_STATIC
                body.collision_layer = 8      # layer 4, Rubble
                body.collision_mask = 1       # collide with World only
                body.position = Vector3(
                    (x + 0.5) * size.x - self.building_size.x * 0.5,
                    (y + 0.5) * size.y,
                    (z + 0.5) * size.z - self.building_size.z * 0.5)

                var mesh: MeshInstance3D = MeshInstance3D.new()
                var box: BoxMesh = BoxMesh.new()
                box.size = size * 0.98        # small gap, so faces do not z-fight
                mesh.mesh = box
                body.add_child(mesh)

                var col: CollisionShape3D = CollisionShape3D.new()
                var shape_box: BoxShape3D = BoxShape3D.new()
                shape_box.size = size
                col.shape = shape_box
                body.add_child(col)

                self.chunks.add_child(body)

Action: call it from _ready(), after the existing lines:

    self._build_chunks()
    self.chunks.visible = false     # hidden until the building dies
Key point — why collision_layer = 8 and not 4. These properties are bitmasks, not layer numbers. Layer 1 is 1, layer 2 is 2, layer 3 is 4, layer 4 is 8. The pattern is 2 to the power of (layer − 1). Setting 4 here would put your rubble on layer 3, the Buildings layer.
Note — start with 12 chunks. Raise chunk_cols to 3 for 27 chunks once you have seen it run. Increasing the grid raises the count fast, because it is cubic.

3. Release the chunks on collapse

Replace the _collapse() function from Chapter 1 with this version. It hides the intact meshes, shows the chunks, unfreezes them, and pushes each one outward.

@export var blast_force: float = 6.0
@export var debris_lifetime: float = 4.0


func _collapse() -> void:
    self.intact.visible = false
    self.cracked.visible = false
    self.shape.set_deferred("disabled", true)
    self.chunks.visible = true

    for child in self.chunks.get_children():
        var chunk: RigidBody3D = child as RigidBody3D
        if chunk == null:
            continue
        chunk.freeze = false
        var dir: Vector3 = (chunk.global_position
                            - self.global_position).normalized()
        dir.y = absf(dir.y) + 0.4          # bias upward, so it bursts
        chunk.apply_impulse(dir * self.blast_force)
Note — the rubble mesh is no longer shown here. The chunks replace it visually. You will reveal it in the next step, once the debris has settled.
Expected: punch a building to zero health and it bursts into a dozen falling boxes.

4. Clean up after the debris settles

Free the chunks after a few seconds and reveal the rubble pile. Without this, every destroyed building leaves its physics bodies simulating for the rest of the match.

Action: add these lines to the end of _collapse():

    await get_tree().create_timer(self.debris_lifetime).timeout

    for child in self.chunks.get_children():
        child.queue_free()

    self.rubble.visible = true
Key point — this is the step people skip. Twelve chunks per building across ten buildings is 120 rigid bodies, all simulating forever. Freeing them is what keeps the frame rate stable through a whole play session.
Note — tune debris_lifetime in the Inspector. Four seconds is enough for chunks to land and stop moving. Shorter looks abrupt; longer costs performance for no visual gain.
Checkpoint for this chapter: buildings burst into boxes, the boxes land and rest, then they disappear a few seconds later and leave a rubble pile.

Performance

Keeping the frame rate

Bottom line: Aim for tens of simultaneously falling chunks, not hundreds. Watch the actual numbers rather than guessing.

1. Measure before you tune

Godot has a live performance panel; use it instead of guessing.

  1. Run the game with F5.
  2. In the editor, open the Debugger panel at the bottom.
  3. Select the Monitors tab.
  4. Watch Physics Process time while you destroy several buildings at once.
Note — the budget. At 60 frames per second you have 16.6 milliseconds per frame for everything. If physics alone approaches 8 milliseconds, reduce the chunk count.

2. Turn the three dials that matter

All three are exported, so you can tune them in the Inspector without editing code.

SettingStart atEffect
chunk_cols / chunk_rows2 / 3Total chunks per building. Cubic growth — 3 columns means 27 pieces, not 18.
debris_lifetime4.0How long chunks simulate before being freed. The single biggest lever.
blast_force6.0Visual only. Higher scatters debris further without costing performance.
Key point — chunks only cost while unfrozen. A frozen RigidBody3D is nearly free, so a city full of intact buildings runs fine no matter how many chunks each one holds. Cost arrives only when buildings actually fall, which is why debris_lifetime matters more than the chunk count.

3. If it still stutters, cut in this order

Work down this list until the frame rate holds.

  1. Drop debris_lifetime to 2.0.
  2. Drop chunk_rows to 2, giving 8 chunks per building.
  3. Cap concurrent collapses, so only one building can be falling apart at a time.
  4. Revert to the mesh-swap collapse from Chapter 1. It always looks better than a game running at 20 frames per second.
Warning — do not attempt runtime fracture. Computing a fracture pattern while the game runs is CPU-heavy and unpredictable. Pre-fracturing, whether as the box grid above or the Blender shards in Chapter 3, is the correct approach for a jam.
Note — third-party tools, not officially documented. VoronoiShatter (MIT, on the Godot Asset Library) fractures meshes inside the Godot editor; its author labels it "highly experimental" and lists support for Godot 4.2 to 4.6, so 4.7.1 compatibility is unconfirmed. Godot-Destruction is a runtime alternative. Neither is needed for this chapter or for Chapter 3.
