Read this first

The whole plan in five lines

  • Your version guess was right. Godot 4.7.1-stable shipped 14 July 2026. Take the Standard build (GDScript), not .NET.
  • Build in this order: controller → buildings → climbing → punching → destruction → polish. Each phase depends on the one before it.
  • The one non-obvious trap is collision layers. Set them up properly in Phase 2 and half your later bugs never happen.
  • Destruction is pre-fractured chunks as frozen RigidBody3D nodes. You unfreeze them on death. Never compute a fracture while the game is running.
  • There is no free CC0 rigged gorilla. The best model is CC-BY, so budget one line of credits.

Version and API claims below are checked against the official Godot documentation. Third-party and unconfirmed items are labelled inline.

Phase 0

Setup, and a room to stand in

Bottom line: Install the Standard build, create the project, then build a test level with a floor and a light. You need somewhere to stand before you build anything that stands.

1. Download Godot 4.7.1-stable, Standard build

Take the Standard build. The Standard build ships with GDScript — Godot's built-in Python-like scripting language. The .NET build adds C# support plus an external toolchain you do not want to configure this week.

Why it matters: GDScript has the fastest edit-run loop and the best documentation coverage. For a first 3D project, that is the whole argument.

  1. Open the official archive page for 4.7.1-stable.
  2. Download the file for your OS under the heading Standard, not .NET.
  3. Unzip it. Godot is a single executable with no installer — put it wherever you keep tools.
Expected: double-clicking the executable opens the Project Manager, a window listing your existing projects with a Create button at the top.

Source: godotengine.org/download/archive/4.7.1-stable · 4.7.1 release notes

2. Read the five differences from 2D before you click anything

Five things change when you move from 2D to 3D. Everything else — the scene tree, signals, the inspector, attaching scripts — works exactly as it did on your first two projects.

  • Node2D becomes Node3D. Node3D is the base spatial node. Anything with a position in 3D space inherits from it.
  • Y points up. In 3D, +Y is up, +X is right, and -Z is forward. In 2D, +Y pointed down. This will catch you at least once.
  • 1 unit = 1 metre. Physics is tuned around this. Godot's Jolt documentation states dynamic objects should be roughly 0.1 to 10 m long and static objects 0.1 to 2000 m.
  • Transform holds a basis and an origin. The basis is rotation plus scale; the origin is position. Use the position and rotation fields in the Inspector and ignore the basis for now.
  • Nothing renders without a camera and a light. In 2D everything was visible by default. In 3D you must add them yourself.
Key point — viewport navigation. In the 3D viewport: right-mouse-drag to look around, middle-mouse-drag to pan, scroll wheel to zoom. Hold right mouse and use W A S D to fly like a first-person game. Press F with a node selected to focus the view on it — you will use F constantly.
Note — gizmos. Selecting a node shows coloured arrows: red is X, green is Y, blue is Z. The keys Q (select), W (move), E (rotate), R (scale) switch gizmo modes.

3. Create the project and pick the renderer

The renderer is chosen here and is awkward to change later, so decide about web export now. This is the one irreversible-feeling decision in the whole setup.

  1. In the Project Manager, click Create.
  2. Set Project Name to GiantGorilla.
  3. Set Project Path to an empty folder. Godot refuses to create a project in a folder that already has files.
  4. Choose the Renderer:
    • Forward+ — best visuals, desktop only. Pick this if you will ship a downloadable build.
    • Compatibility — OpenGL-based, far more reliable in browsers. Pick this if you need the game to run in a browser.
    • Mobile — not relevant here.
  5. Leave Version Control Metadata on Git if you use Git, otherwise set it to None.
  6. Click Create & Edit.
Expected: the editor opens on an empty scene, with the Scene dock top-left offering Create Root Node: 3D Scene / 2D Scene / User Interface / Other Node.
Warning: if you need a browser-playable build, choose Compatibility now. Switching a Forward+ project to Compatibility later means re-checking every material and light in the game.

Phase 1

A gorilla that walks, jumps, and has a camera behind it

Bottom line: Build the gorilla as its own scene, attach one script to its root node, and add all movement code to that single script. The camera is a SpringArm3D inside the same scene.

Read first — where code lives in this phase. Every snippet in Phase 1 goes into one file: player.gd, attached to the Player node. You will add functions to it across steps 2, 4 and 6. There is no second script until Phase 4.

1. Create the Player scene and set its properties

Build the gorilla in a separate scene file, then place a copy of it in the level. A scene in Godot is a saved tree of nodes; instancing one into another is how you reuse it.

Why CharacterBody3D: the class reference describes these bodies as "not affected by physics at all, but they affect other physics bodies in their path," and gives them "wall and slope detection (move_and_slide method)." You get sliding along walls without writing collision maths.

Action — create the scene and root node:

  1. Choose Scene → New Scene from the menu bar.
  2. In the Scene dock click Other Node, search CharacterBody3D, click Create.
  3. Press F2 and rename it to Player.
  4. Press Ctrl+S and save as res://scene/player.tscn.

Action — add the collision shape (this is the invisible body physics actually uses):

  1. Select Player, press Ctrl+A, add a CollisionShape3D.
  2. In the Inspector set Shape to New CapsuleShape3D.
  3. Click the capsule to expand it. Set Radius to 1.5 and Height to 8.
  4. Still on the CollisionShape3D, set Transform → Position to x 0, y 4, z 0.
Key point — why position Y is 4. A CapsuleShape3D is centred on its own origin, so an 8 m capsule sitting at y 0 would have half of itself below the floor. Raising it by half its height (4 m) puts the gorilla's feet at the node's origin. If your character sinks into the ground or hovers, this value is the cause.

Action — add a placeholder body you can see:

  1. Select Player, press Ctrl+A, add a MeshInstance3D.
  2. Set Mesh to New CapsuleMesh, then expand it and set Radius 1.5, Height 8 to match the collision shape.
  3. Set the MeshInstance3D's Transform → Position to x 0, y 4, z 0, the same as the collision shape.
  4. Rename it to Body. Later steps refer to it by that name.

Action — add the Facing pivot. This node carries everything that has a front: the mesh, the climb ray, and the fist.

  1. Select Player, press Ctrl+A, add a Node3D, rename it to Facing.
  2. Leave its Position and Rotation at 0, 0, 0. This is essential — see the warning below.
  3. Drag Body in the Scene dock so it becomes a child of Facing.
Key point — why a pivot instead of rotating each node. Rotating a node spins it around its own origin. The fist you add in Phase 4 sits 3 m in front of the player, so rotating the fist itself only spins the sphere on the spot; it never swings around the player. Rotating a parent that sits at the player's origin orbits every child around that point, which is what you actually want. One rotated pivot replaces three rotated nodes.
Warning: Facing must stay at position 0, 0, 0. If you offset it, every child orbits around the offset point instead of the player's centre, and the fist will swing in a circle that misses the buildings.
Note — the camera is deliberately not under Facing. CameraPivot stays parented to Player. If the camera turned with the character, mouse-look and character-turning would fight each other every frame.

Action — check the CharacterBody3D settings. The defaults are correct for this game; open the Inspector on Player and confirm rather than change:

PropertyValueMeaning

Up Direction0, 1, 0Which way is up. Decides what counts as floor, wall, or ceiling.
Floor → Max Angle45°Steeper than this counts as a wall, not a floor.

Action — put the gorilla in the level:

  1. Switch to scene/level.tscn using the scene tabs above the viewport.
  2. Select the Level root node.
  3. Click the chain-link icon in the Scene dock toolbar (Instantiate Child Scene, or press Ctrl+Shift+A).
  4. Choose scene/player.tscn.
  5. Set the new Player node's Position to x 0, y 2, z 0 so it starts just above the floor.
Expected: a tall capsule standing on the grey slab in the level viewport. It will not move yet.
Note — keep the placeholder capsule until Phase 6. Swapping in the real gorilla model is a 10-minute job at the end and unblocks nothing before then.

2. Attach the script, then write the gravity, move, and jump loop

The script attaches to the Player node itself, not to any child. A script attached to a node adds behaviour to that node, and extends CharacterBody3D on line 1 is what tells Godot which node type it belongs to.

Action — attach the script:

  1. Open scene/player.tscn and select the Player root node.
  2. Right-click it and choose Attach Script. (The same command is the scroll-with-a-plus icon in the Scene dock toolbar.)
  3. In the dialog, confirm Language is GDScript and Inherits is CharacterBody3D. Both should be filled in already.
  4. Set Template. If the dropdown offers CharacterBody3D: Basic Movement, choose it — Godot writes a working movement script for you. If you do not see it, choose Node: Default.
  5. Leave Built-in Script unticked so the code lives in its own file.
  6. Change the Path. Godot suggests res://scene/player.gd, next to the scene. Overwrite it with res://script/player.gd, then click Create.
Warning — this path defaults to the wrong folder every time. The Attach Script dialog always proposes the folder the scene lives in. Correct it to res://script/ on every script you create, or they will scatter across scene/.
Expected: the editor switches to the Script workspace and player.gd opens. A small script icon now appears beside Player in the Scene dock.

Action — replace the file contents with this. Select everything in the editor and paste over it:

extends CharacterBody3D

@export var speed: float = 8.0
@export var jump_velocity: float = 6.0
@export var gravity: float = 20.0


func _physics_process(delta: float) -> void:
    # 1. Fall when there is no floor underneath.
    if not self.is_on_floor():
        self.velocity.y -= self.gravity * delta

    # 2. Jump only from the ground.
    if Input.is_action_just_pressed("jump") and self.is_on_floor():
        self.velocity.y = self.jump_velocity

    # 3. Read the movement keys into horizontal velocity.
    var input: Vector2 = Input.get_vector("move_left", "move_right",
                                          "move_forward", "move_back")
    self.velocity.x = input.x * self.speed
    self.velocity.z = input.y * self.speed

    # 4. Hand the velocity to the physics engine.
    self.move_and_slide()

What the parts mean:

  • @export makes a variable editable in the Inspector. Select Player and you will see Speed, Jump Velocity and Gravity as fields you can tune while the game is not running.
  • _physics_process(delta) is a function Godot calls automatically at a fixed 60 times per second. All physics and movement code goes here, never in _process.
  • delta is the seconds elapsed since the last physics tick. Multiplying by it keeps speed consistent regardless of frame rate.
  • velocity is a built-in property of CharacterBody3D. You set it; move_and_slide() reads it.
Key point — explicit type hints. var speed: float = 8.0 states the type outright. The shorter var speed := 8.0 makes Godot infer it, and both produce the same float — but the explicit form is checkable at a glance and survives refactoring. Every sample in this guide is fully hinted: variables get : Type, parameters get delta: float, and functions get a return type such as -> void (meaning "returns nothing").
Note — turn the checker on. In Project Settings → Debug → GDScript, set Untyped Declaration and Unsafe Property Access to Warn. The editor will then flag any line where a type is unknown, which is how you catch a typo in a node name before you run the game.
Key point — the self. prefix. self means "this node". Writing self.velocity instead of velocity makes it visually obvious which names are members of this class and which are local variables that vanish at the end of the function. In the block above, speed, gravity and velocity are members and take self.; delta and input are local and do not. Every sample in this guide follows that convention.
Note — self. is style, not behaviour, in Godot 4. Godot 3 tutorials often claim you need self. to trigger a variable's setter function. That stopped being true in GDScript 2.0: setters and getters are now called consistently whether or not you prefix with self.. Use it because it reads clearly, not because it changes what the code does. Verified against the Godot documentation's GDScript reference; the Godot 3 setget behaviour it replaced is described in godot-proposals issue 2979.
Warning — the number one copy-paste bug. In Godot 4, move_and_slide() takes no arguments. Godot 3 tutorials write move_and_slide(velocity) and will not run. If you see an error about argument counts, this is why.
Warning — GDScript uses indentation, like Python. Every line inside a function must be indented one level. Mixing tabs and spaces in the same file produces an "unindent does not match" error. The samples in this guide use four spaces; Godot's own default is tabs. Either works — pick one and keep the whole file consistent. If you paste these samples into a tab-indented file, use Edit → Indentation → Convert Indent to Tabs in the script editor.
Note — why gravity is 20 and not 9.8. Real gravity on a 10 m character looks slow and floaty, because everything falls at the same rate but takes longer to cross a larger body. Doubling it reads as weight. Tune the Inspector value until the jump feels right.
Key point: this will not run yet — the actions jump, move_left and so on do not exist until step 5. If you run now you get an error naming the missing action. That is expected. Do step 5 before testing.

Source: Using CharacterBody2D/3D

3. Build the SpringArm3D camera rig

Three nodes, nested, added inside scene/player.tscn. SpringArm3D is Godot's built-in fix for cameras clipping through walls: the class reference describes it as casting "a ray (or collision shape) along its z axis and moves all its direct children to the collision point, minus a margin."

Why it matters: without it, the camera goes inside buildings the moment the gorilla backs into one — which, in a climbing game, is constantly.

Action — build the chain:

  1. Open scene/player.tscn and select the Player root node.
  2. Press Ctrl+A, add a Node3D, rename it to CameraPivot.
  3. Set CameraPivot's Position to x 0, y 7, z 0 — roughly head height on an 8 m gorilla.
  4. Select CameraPivot, press Ctrl+A, add a SpringArm3D. Leave its position at 0, 0, 0.
  5. Select SpringArm3D, press Ctrl+A, add a Camera3D. Leave its position at 0, 0, 0.
Expected tree: 
Player (CharacterBody3D)  ← player.gd attached here
├── CollisionShape3D
├── Facing (Node3D)          ← the only node that rotates
│   ├── Body (MeshInstance3D)
│   ├── WallRay (RayCast3D)  ← added in Phase 3
│   └── Fist (Area3D)        ← added in Phase 4
└── CameraPivot (Node3D)     ← never rotates with the character

        └── Camera3D

4. Add mouse-look to the same script

Add these to player.gd, below the code you already wrote. Do not create a new script and do not attach anything to the camera.

Action: add the exported variable at the top of the file with the others, then paste the three functions at the bottom.

@export var sensitivity: float = 0.003

# Typed node references, so the editor can check every property you use.
@onready var pivot: Node3D = $CameraPivot
@onready var arm: SpringArm3D = $CameraPivot/SpringArm3D
@onready var facing: Node3D = $Facing          # used from step 6 onward


func _ready() -> void:
    Input.mouse_mode = Input.MOUSE_MODE_CAPTURED


func _input(event: InputEvent) -> void:
    if event is InputEventMouseMotion:
        var motion: InputEventMouseMotion = event as InputEventMouseMotion
        self.pivot.rotate_y(-motion.relative.x * self.sensitivity)
        self.arm.rotate_x(-motion.relative.y * self.sensitivity)
        self.arm.rotation.x = clampf(self.arm.rotation.x,
                                     deg_to_rad(-60.0), deg_to_rad(60.0))


func _unhandled_input(event: InputEvent) -> void:
    if event.is_action_pressed("ui_cancel"):
        Input.mouse_mode = Input.MOUSE_MODE_VISIBLE

What the parts mean:

  • $CameraPivot is shorthand for "the child node named CameraPivot". The path is case-sensitive and must match your node names exactly.
  • The : Node3D part is the type hint. On its own $CameraPivot is only known to be a Node, so the editor cannot tell you whether rotate_y() exists on it. Declaring the type lets it check, and lets autocomplete work.
  • @onready delays the lookup until the node tree is built. Without it, the reference would be null.
  • _ready() runs once when the node enters the scene.
  • _input(event) runs whenever any input arrives, including mouse movement, which _physics_process does not see.
  • clamp stops the vertical look going past 60 degrees up or down, which would flip the camera upside-down.
Key point — ui_cancel is bound to Escape by default, so the last function gives you a way to release the mouse. Without it you cannot get your cursor out of the running game, which makes testing miserable.
Note: if a $CameraPivot line errors with "Invalid access", the node name in the Scene dock does not match the string in the script. Check capitals and spelling.

6. Make movement follow the camera, and turn the gorilla to face it

Two changes to player.gd: rotate the input by the camera's heading, then rotate the mesh toward the direction of travel. This is what turns a floaty test capsule into something that feels like a character.

Action — replace section 3 of _physics_process (the two lines setting velocity.x and velocity.z) with this:

    var input: Vector2 = Input.get_vector("move_left", "move_right",
                                          "move_forward", "move_back")
    # Rotate the input so "forward" means "away from the camera".
    var dir: Vector3 = Vector3(input.x, 0.0, input.y).rotated(
        Vector3.UP, self.pivot.rotation.y)
    self.velocity.x = dir.x * self.speed
    self.velocity.z = dir.z * self.speed

    # Turn the Facing pivot toward the direction of travel.
    # Mesh, ray and fist are its children, so they all turn with it.
    if dir.length() > 0.1:
        var target: float = atan2(-dir.x, -dir.z)
        self.facing.rotation.y = lerp_angle(self.facing.rotation.y,
                                            target, delta * 10.0)

What the parts mean:

  • rotated(Vector3.UP, pivot.rotation.y) spins the raw key input by however far you have swung the camera, so W always means "away from camera".
  • atan2(-dir.x, -dir.z) — both arguments are negated, and that matters. A Node3D's forward is -Z. Rotating by an angle t points it at (-sin t, 0, -cos t), so to face dir you must feed in -dir. Drop the minus signs and everything ends up turned 180 degrees.
  • You rotate Facing, never the individual nodes. The mesh, the climb ray and the fist are all its children, so one line turns all three, and the offset fist orbits the player instead of spinning on the spot.
  • lerp_angle eases toward the new angle and handles the wrap from 359° to 1° correctly. Plain lerp makes the character spin the long way round.
  • delta * 10.0 is the turn speed. Raise it for snappier turning, lower it for a heavier feel.
Warning — a capsule hides this bug. A CapsuleMesh looks identical from every angle, so a 180-degree error is invisible until you add the climb ray in Phase 3 or the fist in Phase 4 and they point behind the gorilla. Test the sign now: walk forward and confirm the blue ray gizmo leads the character rather than trailing it.
Note — why not just rotate the Player root? It would work for the mesh, ray and fist, and the capsule collision shape would not care because it is symmetric around Y. But CameraPivot is also a child of the root, so the camera would swing every time the character turned and fight your mouse-look. The Facing pivot rotates exactly the nodes that should turn and leaves the camera alone.
Checkpoint for Phase 1. You can walk in the direction the camera faces, jump, orbit the camera with the mouse, and the capsule turns to face its direction of travel. Save both scenes with Ctrl+S before moving on.

Phase 2

A city to climb, and the layers that make it work

Bottom line: Make one Building scene, place several copies, then set collision layers on everything. The layer work is the highest-value 30 minutes in this whole guide.

1. Make one Building scene and place five copies

Build one building as a reusable scene, not five separate node trees. When you add health in Phase 4, editing the one scene file updates every copy in the level.

Action — create the building:

  1. Choose Scene → New Scene.
  2. Click Other Node, add a StaticBody3D, rename it to Building.
  3. Press Ctrl+S, save as res://scene/building.tscn.
  4. Select Building, press Ctrl+A, add a CollisionShape3D.
  5. Set its Shape to New BoxShape3D, then set Size to x 12, y 40, z 12.
  6. Set the CollisionShape3D's Position to x 0, y 20, z 0 so the building's base sits at the node origin.
  7. Select Building, press Ctrl+A, add a MeshInstance3D, rename it to Intact.
  8. Set its Mesh to New BoxMesh with Size x 12, y 40, z 12, and its Position to x 0, y 20, z 0.
Expected: a 40 m tower — five times the gorilla's height. Rename the mesh to Intact now, because Phase 5 adds sibling meshes called Cracked and Rubble.

Action — place copies in the level:

  1. Open scene/level.tscn and select the Level root.
  2. Press Ctrl+Shift+A and choose scene/building.tscn.
  3. Move it away from the gorilla using the move gizmo, or type a Position such as x 25, y 0, z 0.

2. Assign collision layers and masks

Layer is what a thing is. Mask is what a thing looks for. The docs define collision_layer as the layers an object appears in, and collision_mask as the layers it scans. Two objects interact if either one's layer appears in the other's mask.

Where to find them: select any physics node, and in the Inspector open the Collision section. You will see two grids of numbered squares labelled Layer and Mask. Hovering a square shows the name you set in Phase 0. Click a square to toggle it.

Action — set each node exactly as follows:

Key point — the SpringArm3D row is the important one. Leaving layer 2 unticked on its mask is what stops the camera colliding with your own gorilla and slamming into its back. Fix that now and the camera problem from Phase 1 disappears.

Phase 3

Climbing, without a physics rewrite

Bottom line: Cast a ray forward. If it hits a building and the climb key is held, switch to a CLIMB state that skips gravity and maps input to vertical movement. That is the entire mechanic.

Four ways to do climbing, ranked by how likely they are to eat your week
  • 1. RayCast3D plus gravity override — recommended. No plugin, about 25 lines, fully under your control.
  • 2. Area3D climb zones on buildings — also fine, but you must author a zone per building.
  • 3. ShapeCast3D — thicker detection, better on corners, slightly more setup.
  • 4. Changing up_direction — avoid. It redefines what counts as floor and wall, and breaks your walking code.

1. Add a forward-facing RayCast3D

A RayCast3D is an invisible line that reports the first thing it hits. It gives you is_colliding(), get_collision_point(), and get_collision_normal() — the normal is the direction the wall surface faces, which you need to lay the gorilla flat against it.

Action:

  1. Open scene/player.tscn and select the Facing node, not the Player root.
  2. Press Ctrl+A, add a RayCast3D, rename it to WallRay.
  3. Set its Position to x 0, y 5, z 0 — chest height on the capsule.
  4. Set Target Position to x 0, y 0, z -2.5. This is a local offset, so it points 2.5 m forward.
  5. Confirm Enabled is ticked.
  6. Under Collision Mask, tick only layer 3 Buildings.
Expected: a thin blue line drawn forward from the capsule's chest in the editor viewport. It is visible in the editor only, not at runtime.
Note — why 2.5 and not 1. The capsule's radius is 1.5 m, so a 1 m ray would end inside the gorilla's own body and never reach a wall. The ray must be longer than the radius.

Source: RayCast3D class reference

2. Restructure player.gd into a state machine

A state machine here is one variable and one match block. You do not need a plugin, a node graph, or extra classes. This step reorganises the script you already have rather than adding to it.

Why restructure: walking and climbing want different rules — one needs gravity, one must ignore it. Trying to express both with if statements inside a single movement function is where climbing implementations usually collapse.

Action — replace the whole of player.gd below the @export lines at the top. This is the complete state machine including _walk(), which is your old _physics_process body moved into a named function:

enum State { WALK, CLIMB, FALL }

@export var climb_speed: float = 5.0

var state: State = State.WALK
@onready var ray: RayCast3D = $Facing/WallRay


func _physics_process(delta: float) -> void:
    match self.state:
        State.WALK:
            self._walk(delta)
            if self.ray.is_colliding() and Input.is_action_pressed("climb"):
                self._enter_climb()
        State.CLIMB:
            self._climb()
        State.FALL:
            self._walk(delta)
            if self.is_on_floor():
                self.state = State.WALK


# Everything that used to sit in _physics_process now lives here.
# Both WALK and FALL call it, because falling is walking without a floor.
func _walk(delta: float) -> void:
    # 1. Fall when there is no floor underneath.
    if not self.is_on_floor():
        self.velocity.y -= self.gravity * delta

    # 2. Jump only from the ground.
    if Input.is_action_just_pressed("jump") and self.is_on_floor():
        self.velocity.y = self.jump_velocity

    # 3. Read the movement keys, rotated to match the camera.
    var input: Vector2 = Input.get_vector("move_left", "move_right",
                                          "move_forward", "move_back")
    var dir: Vector3 = Vector3(input.x, 0.0, input.y).rotated(
        Vector3.UP, self.pivot.rotation.y)
    self.velocity.x = dir.x * self.speed
    self.velocity.z = dir.z * self.speed

    # 4. Turn the Facing pivot toward the direction of travel.
    if dir.length() > 0.1:
        var target: float = atan2(-dir.x, -dir.z)
        self.facing.rotation.y = lerp_angle(self.facing.rotation.y,
                                            target, delta * 10.0)

    # 5. Hand the velocity to the physics engine.
    self.move_and_slide()


func _enter_climb() -> void:
    self.state = State.CLIMB
    # Face into the wall once, on entry, so the gorilla does not jitter.
    # The normal points out of the wall, back at you, so it needs no
    # negation here - unlike the travel direction above.
    var n: Vector3 = self.ray.get_collision_normal()
    self.facing.rotation.y = atan2(n.x, n.z)


func _climb() -> void:
    self.velocity = Vector3.ZERO      # gravity deliberately skipped
    var v: float = Input.get_axis("move_back", "move_forward")
    self.velocity.y = v * self.climb_speed
    self.move_and_slide()

    if not self.ray.is_colliding() or not Input.is_action_pressed("climb"):
        self.state = State.FALL

What the parts mean:

  • enum State { ... } creates three named constants. State.WALK is clearer than remembering that 0 means walking.
  • match is GDScript's switch statement. Exactly one branch runs per physics tick.
  • _walk() holds every line that used to be in _physics_process. Nothing was rewritten, only moved and given a name.
  • FALL calls _walk() too. Falling is just walking with no floor under you, so it needs the same gravity and air-control code. It differs only in how it exits.
  • CLIMB never applies gravity, which is the entire trick. Setting self.velocity = Vector3.ZERO first wipes any leftover falling speed.
  • Input.get_axis returns a value from -1 to 1, so W climbs up and S climbs down.
Warning — three failure modes, all common.
Stuck on the wall: always keep a path back to FALL when the ray stops colliding. That is the last two lines of _climb.
Jitter: align to the wall normal once on entry, in _enter_climb, never every frame.
Stuck at the roofline: when the ray clears the top edge the gorilla drops instead of mantling. The cheap fix is a small upward nudge on leaving CLIMB while moving up; the cheaper fix is to accept it and cut mantling.
Expected: player.gd is now roughly 70 lines: the @export and @onready lines at the top, then _ready, _input, _unhandled_input, _physics_process, _walk, _enter_climb and _climb. There should be no leftover movement code sitting loose in _physics_process. Checkpoint for Phase 3: hold Shift against a building to stick to it, W and S to move up and down, release Shift to drop off. No soft-locks.

Phase 4

Punching, and buildings that feel it

Bottom line: Put an Area3D in front of the gorilla, switch it on for a fifth of a second when you punch, and have it call take_damage() on whatever building it overlaps.

1. Add the fist hitbox

An Area3D detects overlaps without blocking movement. It emits body_entered and body_exited signals when physics bodies pass through it — exactly what a hitbox needs.

Why Area3D: ShapeCast3D and manual shape queries also work, but Area3D needs no per-frame code and is the hardest to get wrong under time pressure.

Action:

  1. Open scene/player.tscn, select the Facing node, not the Player root.
  2. Press Ctrl+A, add an Area3D, rename it to Fist.
  3. Set its Position to x 0, y 5, z -3 — in front of the chest, just past the capsule's surface.
  4. Select Fist, press Ctrl+A, add a CollisionShape3D.
  5. Set its Shape to New SphereShape3D with Radius 2.
  6. Back on Fist, set Collision → Layer to 5 HitDetection and Mask to 3 Buildings only.
  7. Leave Monitoring ticked on.
Warning — leave Monitoring ticked on. An area's overlap list is only refreshed during a physics step, so an area you switch on mid-frame reports nothing. Leaving it on avoids the problem entirely, and one small sphere costs nothing.
Key point — why the Fist goes under Facing. The fist sits 3 m in front of the player, so it must orbit the player as the character turns, not spin on the spot. Putting it under the pivot gives you that for free. Parent it to Player instead and it will stay locked to world-forward no matter which way the gorilla faces; rotate the Area3D itself and you will only spin the sphere in place. Once you import a rigged model in Phase 6, re-parent the Fist to the hand bone.

2. Deal damage when you punch

A punch reads whatever the fist is currently overlapping and damages it. The area tracks what is in range continuously; pressing the button is what turns that into damage.

Action — add to player.gd:

@export var punch_damage: float = 25.0
@export var punch_cooldown: float = 0.4

@onready var fist: Area3D = $Facing/Fist

var punching: bool = false


func _try_punch() -> void:
    if self.punching:
        return
    self.punching = true

    for body: Node3D in self.fist.get_overlapping_bodies():
        if body.has_method("take_damage"):
            body.call("take_damage", self.punch_damage)

    await get_tree().create_timer(self.punch_cooldown).timeout
    self.punching = false

Action: add one line inside _physics_process, before the match block, so punching works in every state:

    if Input.is_action_just_pressed("punch"):
        self._try_punch()

What the parts mean:

  • get_overlapping_bodies() asks the area what is inside it right now, rather than waiting for a signal. That matters because a building the gorilla is already touching never fires body_entered again.
  • has_method("take_damage") checks before calling, so punching the ground does not crash the game.
  • Why body.call("take_damage", ...) and not body.take_damage(...). body is typed as Node3D, and take_damage is not a method of Node3D — the editor would reject the direct call. call() looks the method up by name at runtime, which is what you want when the check on the line above already proved it exists.
  • await ... timeout pauses this function for the cooldown without freezing anything else. punching stays true across that pause.
  • punching is a cooldown. It stops the player machine-gunning punches by holding the button.
Key point — the better version, for later. An AnimationPlayer can hold a Call Method Track that calls a function on an exact animation frame, so damage lands the moment the fist visually connects. Add that in Phase 6 once you have a punch animation. The docs recommend call_deferred for methods doing heavy work from an animation track.

3. Give buildings health and a damage signal

This is your second script, attached to the Building root node in scene/building.tscn. Because every building in the level is a copy of that one scene, all five get it at once.

Action — attach the script:

  1. Open scene/building.tscn and select the Building root node.
  2. Right-click it, choose Attach Script.
  3. Set Template to Node: Default, change the Path to res://script/building.gd, click Create.
  4. Replace the file contents with the code below.
extends StaticBody3D

signal damaged(current_health: float)
signal collapsed

@export var max_health: float = 100.0

var health: float = 0.0


func _ready() -> void:
    self.health = self.max_health


func take_damage(amount: float) -> void:
    if self.health <= 0.0:
        return
    self.health -= amount
    self.damaged.emit(self.health)
    print("Building hit. Health now: ", self.health)
    if self.health <= 0.0:
        self.collapsed.emit()
        self._collapse()


func _collapse() -> void:
    self.queue_free()   # placeholder - replaced in Phase 5

What the parts mean:

  • signal declares an announcement other nodes can subscribe to. The building does not need to know who is listening. Typing its parameter — damaged(current_health: float) — lets the editor check whoever connects to it.
  • health is set in _ready(), not on its declaration line. An @export value you type into the Inspector is applied after the variable initialisers run. Writing var health: float = max_health would silently capture the default 100, ignoring whatever you set per-building in the Inspector.
  • damaged.emit(health) fires that announcement. Phase 5 uses it for mesh swaps and Phase 6 for dust.
  • queue_free() deletes the node safely at the end of the frame. It is a stand-in until Phase 5 gives you a real collapse.
  • The print goes to the Output panel at the bottom of the editor while the game runs. Delete it once you trust the system.
Expected: press F5, walk to a building, click four times. The Output panel prints 75, 50, 25, 0 and the building vanishes on the fourth hit.
Key point: emit damaged on every hit, not just the fatal one. That signal is what drives the mesh swaps in Phase 5 and the dust in Phase 6.

Phase 5

Collapse

Bottom line: Swap the building's mesh at damage thresholds. It is the cheapest destruction that reads clearly on screen, it costs nothing in physics, and you can finish it in about an hour.

1. Get a ruined building model

Download a wrecked skyscraper rather than modelling one. You need two extra looks for each building: damaged, and flattened.

3D Apocalyptic Building / City — Majadroid CC0

Seven low-poly skyscraper ruins plus billboards and wreckage. Pay-what-you-want, so you can enter zero. Attribution is not required. Download it into res://asset/model/.
Note — no download needed if you are short on time. Duplicating your existing box mesh and giving it a darker material works. The ruins pack simply looks far better for the same amount of code.

2. Add the damaged and rubble meshes

Add two more MeshInstance3D nodes beside the one you already have, both hidden at the start. Only one of the three is ever visible.

Action:

  1. Open scene/building.tscn.
  2. Select the existing Intact mesh and press Ctrl+D to duplicate it. Rename the copy to Cracked.
  3. Set Cracked's Mesh to a ruined model from the pack, or give it a darker material: expand Mesh → Material, choose New StandardMaterial3D, and set Albedo → Color to a dark grey.
  4. Duplicate again and rename to Rubble. Set its Mesh → Size to x 14, y 4, z 14 and its Position to x 0, y 2, z 0, so it is a flat pile at ground level.
  5. Select Cracked and Rubble and untick Visible in the Inspector, so only Intact shows at the start.
  6. Keep the node names exactly as written. The @onready lines below refer to them by name.
Expected: the building looks unchanged in the viewport, with two hidden meshes listed under it in the Scene dock.

3. Swap the meshes as damage lands

Listen to the damaged signal you already emit and show whichever mesh matches the current health. Add these lines to script/building.gd.

# Typed references to the three meshes and the collision shape.
@onready var intact: MeshInstance3D = $Intact
@onready var cracked: MeshInstance3D = $Cracked
@onready var rubble: MeshInstance3D = $Rubble
@onready var shape: CollisionShape3D = $CollisionShape3D


func _ready() -> void:
    self.health = self.max_health           # keep this line from Phase 4
    self.damaged.connect(self._on_damaged)


func _on_damaged(current: float) -> void:
    var pct: float = current / self.max_health
    self.intact.visible = pct > 0.5
    self.cracked.visible = pct <= 0.5 and pct > 0.0

    # Small punch of scale, so the swap reads as impact.
    var t: Tween = create_tween()
    t.tween_property(self, "scale", Vector3(1.05, 0.95, 1.05), 0.05)
    t.tween_property(self, "scale", Vector3.ONE, 0.12)
Key point — the scale tween is what sells it. Without it a mesh swap looks like a texture glitch. With a 0.05 second squash and a 0.12 second recovery, players read it as the building taking a hit.

4. Replace the placeholder collapse

Swap the queue_free() stand-in from Phase 4 for a real collapse. The building becomes a rubble pile the gorilla can walk over.

func _collapse() -> void:
    self.intact.visible = false
    self.cracked.visible = false
    self.rubble.visible = true
    self.shape.set_deferred("disabled", true)
Warning — use set_deferred on that last line. Changing a collision shape in the middle of a physics step raises an error. set_deferred applies the change once the step finishes.
Checkpoint for Phase 5: punch a building four times. It darkens after two hits, flattens on the fourth, and you can then walk over where it stood.

Phase 6

Juice, and getting it out the door

Bottom line: Four small effects and a working export are worth more than any additional mechanic. Get the export working before you polish, not after.

1. Dust on every impact

Add a GPUParticles3D to scene/building.tscn and fire it from the damaged signal. A short-lived cloud of small grey quads reads unmistakably as concrete dust.

  1. Select Building, press Ctrl+A, add a GPUParticles3D, rename it to Dust.
  2. Set Process Material to New ParticleProcessMaterial.
  3. Set Draw Passes → Pass 1 to New QuadMesh with Size 1.5, 1.5.
  4. Tick One Shot, untick Emitting, set Amount to 24 and Lifetime to 1.2.
  5. In the process material set Gravity to 0, -2, 0 and Initial Velocity to roughly 4.
  6. Add @onready var dust: GPUParticles3D = $Dust at the top of building.gd, then call self.dust.restart() from _on_damaged to fire it on each hit.

2. Camera shake on every punch

Add a decaying random offset to the camera's local position, in player.gd. Ten lines, and the highest ratio of perceived quality to effort in the whole project.

@onready var cam: Camera3D = $CameraPivot/SpringArm3D/Camera3D

var trauma: float = 0.0


func _process(delta: float) -> void:
    if self.trauma > 0.0:
        self.trauma = maxf(self.trauma - delta * 2.0, 0.0)
        var shake: float = self.trauma * self.trauma * 0.4
        self.cam.position = Vector3(randf_range(-shake, shake),
                                    randf_range(-shake, shake), 0.0)

Action: set trauma = 0.5 inside _try_punch() when a building is hit, and 1.0 when one collapses.

Note: this one belongs in _process, not _physics_process. Visual effects should run at display frame rate; physics should not.

3. Positional sound

Use AudioStreamPlayer3D, not AudioStreamPlayer. The 3D version attenuates with distance, so a building collapsing across the map sounds far away — which sells the scale of the city for free.

  1. Add an AudioStreamPlayer3D to scene/building.tscn, named Hit.
  2. Put the sound file in res://asset/audio/, then drag it from the FileSystem dock onto the node's Stream property.
  3. Add @onready var hit: AudioStreamPlayer3D = $Hit at the top of building.gd, then call self.hit.play() from _on_damaged.
  4. Before playing, set self.hit.pitch_scale = randf_range(0.9, 1.1) so repeated punches do not sound mechanical.
Note: free CC0 sound effects are on kenney.nl — the Impact Sounds pack covers punches and debris.

4. A score counter

One CanvasLayer with one Label, added to scene/level.tscn. A CanvasLayer draws on top of the 3D scene and ignores the camera, which is what makes it usable as a HUD.

  1. Select Level, press Ctrl+A, add a CanvasLayer named HUD.
  2. Add a Label under it. Set its text to Destroyed: 0.
  3. Attach a script to HUD with a score variable and an add_point() function.
  4. In building.gd's _ready(), connect collapsed to that function via get_tree() or a group.
Key point: buildings destroyed is the whole score. Anything more elaborate is scope you do not have.

5. Export — and always ship a downloadable build

Export on day 13 so day 14 is only for fixes. Export templates are a separate download and the first export always surprises someone.

  1. Open Editor → Manage Export Templates and click Download and Install. This is roughly 1 GB.
  2. Open Project → Export, click Add…, choose Windows Desktop.
  3. Click Export Project, pick an empty folder, and untick Export With Debug.
  4. Add a Web preset only if you chose the Compatibility renderer in Phase 0.
  5. For itch.io, zip the exported files with the HTML named index.html at the top level of the zip.
Warning — web export on itch.io. Godot 4 web builds need SharedArrayBuffer and cross-origin isolation. itch.io exposes this as a "SharedArrayBuffer support" checkbox under Embed Options → Frame Options on the project edit page, and serves the game with Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp. 3. Swap the placeholder capsule for the real model

Action:
