Before you start

This chapter edits Chapter 2's code, it does not replace it

Bottom line: Chapter 2 built debris from generated boxes. This chapter feeds real fractured shards into the same Chunks node and the same _collapse() function. Every box-grid line you already wrote stays in the file as a fallback.

Confirm the box-chunk collapse works

Check all four in the running game before continuing. This chapter changes only where the chunks come from, so anything broken now stays broken.

  1. Punching a building to zero health makes it burst into boxes that fall.
  2. The boxes stop moving, disappear after debris_lifetime seconds, and leave the rubble mesh.
  3. script/building.gd contains _build_chunks(), _collapse(), and the @onready var chunks: Node3D reference.
  4. chunk_cols, chunk_rows, blast_force and debris_lifetime all appear in the Inspector.
Key point — what actually improves here. Boxes read as "the building broke". Shards read as "the building broke apart", because the pieces have different sizes, different weights, and edges that interlock as they land. The physics code is identical; only the shapes and masses change.
Note — you need Blender. This chapter uses Blender to cut the fracture pattern before the game runs. Blender is free at blender.org. Budget one evening if you have never opened it.

Understand the plan before you open Blender

You will fracture a building-shaped mesh once, export the pieces, and let a script turn them into physics bodies at load time. Read this list first so the individual steps make sense.

  1. Blender cuts one mesh into roughly 20 loose fragments.
  2. You export those fragments as a single .glb file.
  3. Godot imports it as a scene containing 20 MeshInstance3D nodes and nothing else.
  4. A new function in building.gd walks those nodes and wraps each one in a frozen RigidBody3D with its own collision shape.
  5. _collapse() is untouched. It unfreezes whatever is under Chunks, exactly as before.
Key point — why a script and not manual editor work. Wrapping 20 fragments by hand takes 20 repetitions of a five-click operation, and you repeat all of it every time you re-fracture. The script does it in one pass, works for any fragment count, and means the only manual asset step is the export.
Expected: you can state, without looking, which piece of software does the fracturing and which does the physics-body creation.

Phase 1 · Blender

Cut the fracture pattern

Bottom line: Cell Fracture splits one mesh into many irregular closed pieces. It is an optional add-on, not a built-in tool, so the first job is installing it.

1. Install the Cell Fracture extension

Cell Fracture is no longer bundled with Blender. It shipped inside Blender up to version 4.1. From Blender 4.2 onward it lives on the Blender Extensions site and you install it yourself, once.

  1. Open Blender and choose Edit → Preferences.
  2. Select the Get Extensions tab.
  3. Type cell fracture into the search field.
  4. Click Install on the Cell Fracture result.
  5. Switch to the Add-ons tab and confirm the checkbox next to Cell Fracture is ticked.
Warning — do not follow older tutorials on this point. Guides written before Blender 4.2 tell you to enable Cell Fracture in Preferences → Add-ons with no installation step. On current Blender the add-on is simply absent until you install it, and the checkbox those guides describe does not exist yet.
Expected: the viewport menu Object → Quick Effects now lists Cell Fracture.

2. Prepare the mesh you are going to break

Cell Fracture needs one closed mesh with clean transforms. "Closed" means the surface has no holes: a solid cube is closed, a cube with a missing face is not.

  1. Delete the default cube's light and camera, keeping only the cube.
  2. Press N to open the sidebar and set the cube's Dimensions to 12 m, 12 m, 40 m. Blender's up axis is Z, so height goes in the third field.
  3. Press Ctrl+A and choose All Transforms. This bakes the scaling into the mesh data.
  4. Move the cube so its base sits on the world origin, then press Ctrl+A → All Transforms again.
Key point — why "Apply All Transforms" matters twice. Blender stores scale and position as instructions layered on top of the mesh, not as changes to the mesh itself. Cell Fracture reads the raw mesh, so unapplied scale produces fragments at the wrong size. Applying transforms rewrites the vertices so what you see is what the add-on gets.
Note — using the real building instead. Majadroid's apocalyptic building pack from Chapter 1 ships its source .blend file. Open it and fracture the skyscraper mesh instead of a cube. Everything below is identical.
Expected: the sidebar shows Scale 1, 1, 1 and Location 0, 0, 0, with dimensions still 12 by 12 by 40.

3. Run Cell Fracture

Twenty fragments is the target. Fewer looks blocky; many more costs frame rate for detail nobody sees during a two-second collapse.

  1. Select the cube by left-clicking it.
  2. Choose Object → Quick Effects → Cell Fracture.
  3. Set Source Limit to 20.
  4. Set Noise to 0.00 for straight-edged concrete-style breaks. Values near 0.50 give ragged organic edges.
  5. Leave every other field at its default and click OK.
Note — the operator panel is collapsed at first. After clicking Cell Fracture a small panel appears in the bottom-left of the viewport. Click it to expand it, then adjust the values. Changing a value re-runs the fracture immediately, so you can experiment.
Warning — the split is not always complete. Cell Fracture sometimes leaves a gap where a fragment should be, or produces a piece offset from the source. If the result looks wrong, change Source Limit by one and let it re-run, which reshuffles the pattern.
Expected: the Outliner lists roughly 20 new objects whose names end in _cell, sitting inside the original cube's volume.

4. Clean up the result

Delete the original and confirm the fragment count before exporting. The original mesh still exists, hidden inside the fragments, and exporting it would put a solid building inside your debris.

  1. In the Outliner, click the original cube (the one without a _cell suffix).
  2. Press X and confirm Delete.
  3. Press A in the viewport to select all remaining fragments.
  4. Press Ctrl+A and choose All Transforms once more.
  5. Count the objects in the Outliner and write the number down. You will check it again in Godot.
Key point — apply transforms on the fragments too. Cell Fracture gives each fragment its own origin point offset from the world centre. Applying transforms bakes those offsets into the vertex positions, so each fragment carries its own location inside its mesh data. That is what lets the Godot script place bodies correctly without any extra maths.
Expected: roughly 20 objects in the Outliner, no original cube, and the sidebar showing Location 0, 0, 0 for whichever fragment you click.

5. Export as glTF

glTF, file extension .glb, is the format Godot's documentation recommends for 3D models. A single .glb holds all 20 fragments.

  1. Press A to select all fragments.
  2. Choose File → Export → glTF 2.0 (.glb/.gltf).
  3. In the export sidebar, set Format to glTF Binary (.glb).
  4. Open the Include section and tick Limit to → Selected Objects.
  5. Name the file building_fragments.glb and save it into your Godot project at res://asset/model/.
Note — the axis conversion is already correct. Blender treats Z as up and Godot treats Y as up. The glTF exporter's default +Y Up setting converts this for you. Do not change it.
Checkpoint: building_fragments.glb exists in asset/model/ and Godot's FileSystem dock shows it after the editor regains focus.

Phase 2 · Godot

Turn the fragments into physics bodies

Bottom line: One new exported property and one new function. When the property is empty you get Chapter 2's boxes; when it points at the fragment scene you get shards.

6. Inspect what Godot imported

Check the fragment count matches Blender before writing any code. A mismatch here means the export was wrong, and every later step would fail confusingly.

  1. In the FileSystem dock, double-click building_fragments.glb.
  2. The Advanced Import Settings dialog opens with a preview and a node tree on the left.
  3. Count the MeshInstance3D entries in that tree.
  4. Click Reimport to close the dialog without changing anything.
Key point — no collision shapes are imported, and that is correct. Godot can generate collision at import time using name suffixes such as -col or -rigid on the Blender objects. This chapter does not use them, because the script builds shapes that you control directly: convex, on the right collision layer, frozen until the building dies.
Expected: the same number of MeshInstance3D nodes as objects you counted in Blender's Outliner.

7. Add the fragment-source property

Add this near the other exported values at the top of script/building.gd. A PackedScene is a scene file stored as a value, so this property lets you point at the imported .glb from the Inspector.

# Leave empty to use the generated box grid from Chapter 2.
# Assign building_fragments.glb to use real fractured shards.
@export var fragment_scene: PackedScene = null

Action: assign it in the editor.

  1. Open scene/building.tscn and select the Building root node.
  2. Find Fragment Scene in the Inspector.
  3. Drag building_fragments.glb from the FileSystem dock onto that field.
Note — this is the switch between chapters. Clearing this field returns you to the box grid with no code changes. Keep it in mind while tuning performance later: it is the fastest way to test whether shards are what is costing you frame rate.
Expected: the Inspector shows Fragment Scene holding building_fragments.glb rather than <empty>.

8. Write the fragment builder

Add this new function to script/building.gd, below _build_chunks(). It instantiates the imported scene, then converts every mesh it finds into a frozen physics body.

func _build_fragment_chunks() -> void:
    var source: Node3D = self.fragment_scene.instantiate() as Node3D

    for child in source.get_children():
        var mesh_node: MeshInstance3D = child as MeshInstance3D
        if mesh_node == null:
            continue

        var body: RigidBody3D = RigidBody3D.new()
        body.freeze = true
        body.freeze_mode = RigidBody3D.FREEZE_MODE_STATIC
        body.collision_layer = 8      # layer 4, Rubble
        body.collision_mask = 1       # collide with World only
        body.transform = mesh_node.transform

        var col: CollisionShape3D = CollisionShape3D.new()
        col.shape = mesh_node.mesh.create_convex_shape()
        body.add_child(col)

        var visual: MeshInstance3D = MeshInstance3D.new()
        visual.mesh = mesh_node.mesh
        body.add_child(visual)

        self.chunks.add_child(body)

    source.queue_free()
Key point — why convex and never concave. create_convex_shape() returns a ConvexPolygonShape3D, a solid hull with no dents. Godot's documentation is explicit that concave shapes are for static level geometry, not for moving bodies. A concave shape on a falling shard behaves unpredictably and costs far more to simulate.
Note — the fragments are convex already. Cell Fracture produces convex cells by construction, so the hull matches the visible shape almost exactly. This is the reason a fractured mesh is a better fit for physics than an arbitrary model.
Expected: the script saves with no errors. Nothing changes in the game yet, because nothing calls this function.

9. Choose between boxes and shards at load

Replace the self._build_chunks() line in _ready() with this branch. It picks the fragment builder when a scene is assigned and falls back to the box grid when it is not.

    if self.fragment_scene != null:
        self._build_fragment_chunks()
    else:
        self._build_chunks()

    self.chunks.visible = false     # hidden until the building dies
Key point — keep _build_chunks() in the file. Deleting it would save nothing and cost you the fallback. If Blender misbehaves, clearing one Inspector field gets you back to working destruction.
Warning — do not also delete the Chunks node. Both builders add their output to it, and _collapse() reads it. It stays exactly where Chapter 2 put it, at position 0, 0, 0 under Building.
Checkpoint: punch a building to zero health and it bursts into irregular shards instead of boxes, using the _collapse() code you have not touched.

Phase 3 · Feel

Make the debris carry weight

Bottom line: Equal-mass shards drift like polystyrene. Two small changes make big pieces land heavily and small pieces skitter.

10. Give each shard a mass from its size

Add these three lines inside the loop in _build_fragment_chunks(), just after body.transform is set. An AABB is the axis-aligned bounding box: the smallest upright box containing the mesh.

@export var chunk_density: float = 0.6


# ... inside the loop, after body.transform = mesh_node.transform
        var extents: Vector3 = mesh_node.mesh.get_aabb().size
        var volume: float = extents.x * extents.y * extents.z
        body.mass = maxf(volume * self.chunk_density, 0.5)
Key point — why the bounding box and not the true volume. Measuring a mesh's real volume is slow and fiddly. The bounding box overestimates slightly for every shard, which means the relative weights stay right even though the absolute numbers are not. Relative weight is the only part the eye can see.
Note — the maxf floor prevents a specific bug. A very thin sliver has almost zero bounding-box volume, so its mass would round to near zero and the blast impulse would fling it across the map. Clamping to 0.5 keeps slivers on stage.
Expected: large shards fall fast and settle immediately; small shards bounce once or twice before stopping.

11. Scale the blast by mass, not against it

Change one line in _collapse() so heavy pieces are not thrown as far as light ones. apply_impulse() applies a fixed push, and a fixed push moves a light body much further than a heavy one, which is correct physics but reads as weak.

Action: find this line in _collapse():

        chunk.apply_impulse(dir * self.blast_force)

Replace it with:

        chunk.apply_impulse(dir * self.blast_force * sqrt(chunk.mass))
Key point — why the square root. Multiplying by mass exactly would give every shard the same launch speed, which looks artificial and uniform. The square root sits between the two extremes: heavy pieces still move less than light ones, but not so much less that they appear glued in place.
Note — this line does nothing without step 10. Boxes from Chapter 2 all share the default mass of 1.0, and the square root of one is one. The change is harmless in box mode and only takes effect for shards.
Expected: the collapse reads as a building coming apart under its own weight rather than an explosion.

12. Re-measure the cost

Convex shards cost more than boxes, so check the numbers before you decide the chapter is finished. Chapter 2's box grid is 12 bodies with 6-face shapes. Twenty shards with 10-to-20-face hulls is more work per contact.

  1. Run the game with F5.
  2. Open the Debugger panel and select the Monitors tab.
  3. Destroy three buildings in quick succession.
  4. Read Physics Process at the peak.
Key point — the budget is unchanged from Chapter 2. At 60 frames per second you have 16.6 milliseconds per frame in total. If physics alone passes 8 milliseconds, act on it before adding anything else to the game.
Note — cut in this order. First drop debris_lifetime to 2.0. Then re-fracture in Blender with Source Limit at 12. Only then consider clearing Fragment Scene to fall back to boxes.
Expected: a peak Physics Process figure you have written down, so a later chapter can be compared against it.

Phase 4 · Troubleshooting

When it breaks

Bottom line: Four failures account for nearly everything that goes wrong here. Each has a distinctive symptom, so identify the symptom first rather than changing values at random.

13. Match the symptom to the cause

Find your symptom in the left column. Work through the table top to bottom, because the earlier faults also produce the later symptoms.

SymptomCauseFix
Nothing appears on collapseFragment Scene is empty, or the .glb holds groups rather than meshesRe-check step 7, then re-export from Blender with only fragments selected
All shards sit stacked at one pointTransforms were not applied to the fragments in BlenderRedo step 4, item 4
Shards jitter violently on spawnConvex hulls overlap because the fracture left no gapRe-run Cell Fracture with Margin slightly above zero
Shards fall through the groundcollision_mask is wrong, so they ignore the World layerConfirm body.collision_mask = 1 in step 8
Warning — do not fracture at runtime. Computing a fracture pattern while the game runs is CPU-heavy and unpredictable. Everything in this chapter happens before the player presses play, which is why it is affordable.
Note — third-party alternatives, not officially documented. VoronoiShatter (MIT, on the Godot Asset Library) fractures meshes inside the Godot editor and would remove the Blender step entirely. Its author labels it "highly experimental" and lists support for Godot 4.2 to 4.6, so 4.7.1 compatibility is [Unverified]. Nothing in this chapter needs it.
Checkpoint for Chapter 3: buildings collapse into weighted irregular shards, the shards clear themselves after debris_lifetime, and clearing one Inspector field still returns you to Chapter 2's boxes.
